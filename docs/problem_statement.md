# Problem Statement: ระบบช่วยตรวจสอบสินค้าที่มีความเสี่ยงขาดสต็อก

บริษัทสมมติ: BaanDee Living (ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์) · สถานะเอกสาร: ฉบับร่าง v0.1

## 1. สรุปสั้น
เจ้าหน้าที่จัดซื้อต้องตัดสินใจทุกวันว่าสินค้ารายการไหนต้องสั่งเพิ่มก่อน แต่ข้อมูลที่ใช้ตัดสินใจกระจายอยู่หลายที่ (ยอดขาย สต็อก ระยะเวลาที่ซัพพลายเออร์ส่งของ) ต้นแบบนี้รวมข้อมูลเหล่านั้นเพื่อชี้ว่า SKU ไหนมีความเสี่ยงที่ของจะหมดก่อนของใหม่มาถึง พร้อมแสดงหลักฐาน แหล่งที่มาและเวลาของข้อมูล แยกข้อเท็จจริงออกจากค่าประมาณ และหยุดส่งต่อให้คนตรวจเมื่อข้อมูลไม่พอหรือกำกวม แทนการเดา

ต้นแบบนี้เป็นเครื่องมือช่วยตัดสินใจ ไม่ได้สั่งซื้อแทนคน และทดสอบกับข้อมูลสังเคราะห์เท่านั้น

## 2. ผู้ใช้หลัก
- ผู้ใช้หลัก: เจ้าหน้าที่จัดซื้อ/วางแผนสต็อกของ BaanDee Living (ตัวละครสมมติ)
- ผู้ใช้รอง: หัวหน้าฝ่ายจัดซื้อ ผู้อนุมัติคำขอสั่งซื้อ

## 3. งานที่ผู้ใช้กำลังพยายามทำ
ตัดสินใจในแต่ละวันว่าควรขอสั่งซื้อสินค้ารายการใด จำนวนเท่าไร และเร่งด่วนแค่ไหน ก่อนที่สินค้าจะหมด โดยต้องเทียบ 3 อย่างเข้าด้วยกัน
1. สต็อกที่เหลือตอนนี้
2. สินค้านั้นขายเร็วแค่ไหน
3. ถ้าสั่งวันนี้ ของจะมาถึงในกี่วัน (lead time)

## 4. ปัญหาของกระบวนการปัจจุบัน (สมมติฐานของทีม ยังไม่ได้สัมภาษณ์หรือสังเกตผู้ใช้จริง)
| # | ปัญหา | ผลที่อาจเกิดขึ้น |
|---|---|---|
| 4.1 | ข้อมูลยอดขาย สต็อก และ lead time เก็บแยกกัน ต้องเปิดเทียบด้วยมือ | เสียเวลาและตกหล่นง่าย |
| 4.2 | ไม่มีเกณฑ์กลางว่าแบบไหนคือ "เสี่ยง" แต่ละคนใช้วิจารณญาณต่างกัน | ลำดับความเร่งด่วนไม่สม่ำเสมอ |
| 4.3 | สต็อกอย่างเดียวบอกความเร่งด่วนไม่ได้ (เหลือ 10 ชิ้นแต่ขายช้า ไม่เร่งเท่าเหลือ 10 ชิ้นแต่ขายวันละ 3 ชิ้น) | สั่งช้าเกินไปหรือสั่งผิดตัว |
| 4.4 | ข้อมูลที่ไม่ครบหรือเก่าไม่ถูกแจ้งเตือน (เช่น ไม่รู้ lead time, สต็อกดึงมาเมื่อไหร่) | ตัดสินใจจากข้อมูลที่ไม่น่าเชื่อถือโดยไม่รู้ตัว |

## 5. ต้นแบบช่วยให้ดีขึ้นอย่างไร
| ปัญหา | สิ่งที่ต้นแบบทำ |
|---|---|
| 4.1 | รวมข้อมูลสองแหล่งด้วย `product_id` และแสดงในหน้าจอเดียว |
| 4.2 | ใช้กฎที่เขียนชัดเจนและเหมือนกันทุกครั้ง: เปรียบเทียบ days of cover กับ lead time แล้วจัดระดับความเสี่ยง |
| 4.3 | คำนวณ "สต็อกพอขายกี่วัน" จากยอดขายเฉลี่ยต่อวัน ไม่ใช้สต็อกดิบอย่างเดียว |
| 4.4 | แสดงเวลาของข้อมูลทุกชิ้น ป้ายแยก "ข้อเท็จจริงที่ยืนยันแล้ว" กับ "ค่าประมาณ" และส่งต่อคนเมื่อข้อมูลไม่พอ |

## 6. ลำดับการทำงานและผลลัพธ์ของระบบ
เลือก SKU → ระบบดึงสต็อก ยอดขาย และ lead time → คำนวณความเสี่ยง → แสดงผลพร้อมหลักฐาน → เจ้าหน้าที่บันทึกคำขอสั่งซื้อ (draft) → แก้ไข/อนุมัติสถานะ → ข้อมูลถูกเก็บถาวรและเรียกกลับมาดูได้

| ผลลัพธ์ | ความหมาย |
|---|---|
| ขาดสต็อกแล้ว | สต็อก = 0 (เป็นข้อเท็จจริงจาก snapshot) |
| ความเสี่ยงสูง | days of cover น้อยกว่า lead time (สั่งวันนี้ก็อาจไม่ทัน) |
| ความเสี่ยงกลาง | days of cover มากกว่า lead time แต่ยังไม่เกินส่วนเผื่อ |
| ความเสี่ยงต่ำ | มีเวลาเหลือพอ |
| ต้องให้คนตรวจ | ข้อมูลไม่พอหรือกำกวม ระบบไม่ประเมินและไม่เดา |

## 7. ขอบเขต
**อยู่ในขอบเขต:** สินค้า 82 SKU ในคลังเดียว (BKK-DC) ตามข้อมูล snapshot · คำนวณความเสี่ยงด้วยกฎที่เขียนชัดเจน (ไม่ใช้ AI) · หน้าจอเลือก SKU และแสดงหลักฐาน · บันทึก/แก้ไข/อนุมัติ/ลบแบบ soft delete คำขอสั่งซื้อ (reorder request) · ทดสอบอัตโนมัติอย่างน้อย 5 กรณี

**นอกขอบเขต:** ไม่สั่งซื้อจริงและไม่เชื่อมระบบจริงของบริษัทหรือมหาวิทยาลัย · ไม่พยากรณ์ยอดขายด้วยโมเดลสถิติหรือ machine learning · ไม่รองรับหลายคลัง/หลายสาขา · ไม่คำนวณจำนวนสั่งที่เหมาะสมที่สุดทางเศรษฐศาสตร์ (เช่น EOQ) ระบบเสนอเพียงจำนวนขั้นต่ำตามข้อมูลซัพพลายเออร์ · ไม่ตัดสินแทนมนุษย์ คนเป็นผู้อนุมัติเสมอ

## 8. ข้อมูลที่ใช้
| แหล่ง | ที่มา | ใช้ทำอะไร |
|---|---|---|
| แหล่งที่ 1: orders, order_lines, products, inventory_snapshot | ชุด BaanDee ที่อาจารย์ให้ (`data/raw/`) | ยอดขาย สต็อก หมวดและราคาสินค้า |
| แหล่งที่ 2: supplier_lead_time | ทีมสร้างเอง (สังเคราะห์ด้วยสคริปต์ที่ตั้ง random seed) ใน `data/generated/` | ระยะเวลาที่ซัพพลายเออร์ส่งของ ซึ่งข้อมูลอาจารย์ไม่มี |
| ข้อมูลที่ระบบสร้าง: reorder_requests | ผู้ใช้บันทึกผ่านหน้าจอ เก็บใน `data/app_state/` | บันทึกการตัดสินใจ |

Key ที่ใช้เชื่อม: `product_id` (และ `order_id` ระหว่าง orders กับ order_lines)
เหตุผลที่ต้องมีแหล่งที่ 2: ถ้าไม่มี lead time ระบบจะรู้แค่ว่าสต็อกพอขายกี่วัน แต่ตอบไม่ได้ว่า "สั่งช้าไปแล้วหรือยัง"

## 9. ผลลัพธ์ที่อ้างได้ กับสมมติฐานที่ยังต้องทดลอง
### 9.1 สิ่งที่ยืนยันได้จากข้อมูลที่ตรวจแล้ว (ตรวจเบื้องต้น ต้องตรวจซ้ำหลังทำความสะอาด)
| ข้อเท็จจริง | ที่มา |
|---|---|
| ข้อมูลมี 82 SKU ในคลังเดียว | products.csv, inventory_snapshot.csv |
| สต็อกวัด ณ 31 ก.ค. 2026 06:00 และเก่ากว่าวันที่ใช้งานจริง | inventory_snapshot.csv |
| มี SKU 2 รายการที่สต็อก = 0 | inventory_snapshot.csv |
| ข้อมูลดิบมีปัญหาจริง: รูปแบบวันที่ปน ชื่อหมวดสะกดไม่ตรง รหัส SKU รูปแบบต่างกัน | docs/data_quality_findings.csv |

### 9.2 สมมติฐานที่ยังไม่พิสูจน์ (ต้องทดลองกับผู้ใช้จริง)
| # | สมมติฐาน | วิธีทดสอบถ้าจะทำต่อ |
|---|---|---|
| H1 | เจ้าหน้าที่จัดซื้อใช้เวลาตรวจรายการเสี่ยงน้อยลงเมื่อมีหน้าจอรวมข้อมูล | จับเวลาเทียบงานเดียวกันก่อน/หลังใช้ระบบ ในผู้ใช้อย่างน้อย 5 คน |
| H2 | กฎที่ใช้ชี้รายการเสี่ยงได้ตรงกับการตัดสินใจของผู้เชี่ยวชาญ | ให้ผู้เชี่ยวชาญจัดอันดับ SKU เอง แล้วเทียบกับผลของระบบ |
| H3 | ป้าย "ข้อมูลไม่พอ ต้องให้คนตรวจ" ทำให้ผู้ใช้เชื่อผลลัพธ์อย่างเหมาะสมขึ้น | สังเกตว่าผู้ใช้ตรวจซ้ำในรายการที่ถูกป้ายหรือไม่ |
| H4 | ค่า lead time ที่ใช้ใกล้เคียงของจริง | ทดสอบไม่ได้ในโปรเจกต์นี้ เพราะเป็นข้อมูลสังเคราะห์ |

**ข้อห้ามของทีม:** ไม่เขียนว่าระบบ "ลดเวลาได้ X%", "ลดการขาดสต็อกได้ X%" หรือ "ประหยัดเงิน X บาท" เพราะยังไม่มีหลักฐานจากผู้ใช้จริง สิ่งที่ต้นแบบแสดงได้คือกลไกทำงานได้และตรวจสอบได้ ไม่ใช่ผลทางธุรกิจ

## 10. ข้อจำกัดและความเสี่ยงที่ทราบแล้ว
| ข้อจำกัด | ผลต่อความน่าเชื่อถือ | วิธีรับมือ |
|---|---|---|
| lead time เป็นข้อมูลสังเคราะห์ | รายการ "เสี่ยง" ส่วนหนึ่งเป็นผลจากค่าที่ทีมตั้ง | ระบุใน README และหน้าจอว่าเป็นข้อมูลสาธิต |
| ยอดขายต่อ SKU น้อย (ราว 18 บรรทัดออเดอร์ต่อ SKU ใน 3 เดือน) | ค่าเฉลี่ยต่อวันแกว่งได้ | แสดงเป็น "ค่าประมาณ" ส่งต่อคนเมื่อข้อมูลน้อยกว่าเกณฑ์ ทดสอบเทียบช่วง 30 และ 90 วัน |
| สต็อกมี snapshot เดียว ไม่มีประวัติ | ไม่รู้ว่าสต็อกลดเร็วแค่ไหน | ใช้ยอดขายเป็นตัวแทน และแสดงเวลาข้อมูล |
| ไม่ทราบว่าสถานะ processing หักสต็อกแล้วหรือยัง | ยอดขายอาจนับเกิน/ขาด | ตั้งสมมติฐานและบันทึกใน decision_log.md |
| ยอดขายที่เห็นอาจต่ำกว่าความต้องการจริงเมื่อสินค้าหมดสต็อก | ประเมินความเร่งด่วนต่ำเกินไป | ระบุเป็นข้อจำกัด |
| ใช้วันที่ snapshot (31 ก.ค. 2026) เป็น "วันนี้" ของระบบ | ถ้าใช้วันจริง ยอดขาย 30 วันย้อนหลังจะเป็นศูนย์ | ตั้งเป็นพารามิเตอร์และบันทึกเหตุผล |

## 11. ความปลอดภัยและความรับผิดชอบ
- ใช้เฉพาะข้อมูลสังเคราะห์ ไม่มีข้อมูลส่วนบุคคลจริง ไม่เชื่อมระบบจริงขององค์กรหรือมหาวิทยาลัย
- มนุษย์เป็นผู้ตัดสินใจเสมอ: ระบบเสนอและบันทึกคำขอเป็นสถานะ draft ผู้ใช้ต้องอนุมัติเอง
- ไม่ลบข้อมูลจริง ใช้ soft delete
- ไม่เดาข้อมูลที่กำกวม: รายการที่ตรวจสอบไม่ได้ถูกกักกันไว้ให้คนทบทวน
- ไม่ใช้ AI/LLM เพราะกฎคำนวณความเสี่ยงเป็นสูตรชัดเจนที่ตรวจสอบและทดสอบได้ การใช้ AI ไม่เพิ่มคุณค่าและเพิ่มความเสี่ยงที่ผลลัพธ์จะสร้างตัวเลขที่ไม่มีหลักฐาน (เหตุผลฉบับเต็มอยู่ใน AI_USE.md)

- [ ] มีกรณีสำเร็จอย่างน้อย 1 กรณี และกรณีที่ระบบหยุดส่งต่อคนอย่างน้อย 1 กรณี
