## 1. ปัญหา ผู้ใช้ และคุณค่าที่คาดหวัง

1. **ผู้ใช้หลัก:** เจ้าหน้าที่จัดซื้อ/วางแผนสต็อก (ผู้ใช้รอง: หัวหน้าฝ่ายจัดซื้อผู้อนุมัติคำขอสั่งซื้อ)
2. **งานที่ผู้ใช้ทำ:** ตัดสินใจทุกวันว่าควรขอสั่งซื้อสินค้ารายการใด จำนวนเท่าไร เร่งด่วนแค่ไหน ก่อนสินค้าหมด โดยเทียบสต็อกคงเหลือ ความเร็วในการขาย และ lead time ของซัพพลายเออร์
3. **ปัญหาปัจจุบัน (สมมติฐานของทีม ยังไม่ได้สัมภาษณ์ผู้ใช้จริง):** ข้อมูลยอดขาย สต็อก และ lead time เก็บแยกกัน ไม่มีเกณฑ์กลางของคำว่า "เสี่ยง" สต็อกอย่างเดียวบอกความเร่งด่วนไม่ได้ และข้อมูลที่ไม่ครบหรือเก่าไม่ถูกแจ้งเตือน
4. **ต้นแบบช่วยอย่างไร:** รวมข้อมูลด้วย `product_id` ในหน้าจอเดียว จัดระดับความเสี่ยงด้วยกฎที่ชัดเจนจาก days of cover เทียบ lead time แสดงหลักฐาน แหล่งที่มา เวลาของข้อมูล แยก "ข้อเท็จจริง" จาก "ค่าประมาณ" และส่งต่อคนเมื่อข้อมูลไม่พอ
5. **สมมติฐานที่ยังต้องทดลองกับผู้ใช้จริง:** เวลาตรวจรายการเสี่ยงลดลงหรือไม่ (H1), กฎตรงกับการตัดสินใจของผู้เชี่ยวชาญหรือไม่ (H2), ป้าย "ต้องให้คนตรวจ" ทำให้เชื่อผลอย่างเหมาะสมหรือไม่ (H3), lead time ใกล้ของจริงหรือไม่ (H4 ทดสอบไม่ได้ในโปรเจกต์นี้)

> ทีมไม่อ้างตัวเลขผลทางธุรกิจ (เช่น "ลดการขาดสต็อก X%") เพราะยังไม่มีหลักฐานจากผู้ใช้จริง รายละเอียดเต็มอยู่ที่ [`docs/problem_statement.md`](docs/problem_statement.md)

## 3. Architecture และเหตุผลเลือกเครื่องมือ

| ส่วน | เครื่องมือ | หน้าที่ |
|---|---|---|
| ทำความสะอาดและเชื่อมข้อมูล | Python + pandas (`scripts/`) | raw → cleaned/quarantine, correction log |
| กฎความเสี่ยง | `src/risk.py` | คำนวณ days of cover เทียบ lead time จัด 5 ระดับ |
| ขอบเขตระหว่างระบบ | FastAPI (`api/main.py`) + `src/api_client.py` | ส่งข้อมูล lead time/สต็อกให้ UI ผ่าน HTTP จัดการ พบข้อมูล / ไม่พบ / ใช้งานไม่ได้ |
| หน้าจอ | Gradio (`src/app.py`) | เลือก SKU แสดงหลักฐาน แยกข้อเท็จจริง/ค่าประมาณ จัดการคำขอสั่งซื้อ |
| เก็บข้อมูลถาวร | JSON/CSV (`src/storage.py`) | สร้าง แก้ไข อนุมัติ soft delete คำขอสั่งซื้อ |

**กฎความเสี่ยง** (ค่าเริ่มต้น ต้องยืนยันใน [`docs/decision_log.md`](docs/decision_log.md)):

`days_of_cover = available_qty ÷ ยอดขายเฉลี่ยต่อวัน (30 วัน)`

| ผลลัพธ์ | เงื่อนไข |
|---|---|
| ขาดสต็อกแล้ว | `available_qty = 0` |
| ความเสี่ยงสูง | `days_of_cover < lead_time` |
| ความเสี่ยงกลาง | `lead_time ≤ days_of_cover ≤ lead_time + 7` |
| ความเสี่ยงต่ำ | `days_of_cover > lead_time + 7` |
| ต้องให้คนตรวจ | ไม่มี lead time / ยอดขายน้อยกว่าเกณฑ์ / ข้อมูลถูกกักกัน |

**เหตุผลที่ไม่ใช้ Generative AI ในตัวผลิตภัณฑ์:** กฎเป็นสูตรที่ตรวจสอบและทดสอบซ้ำได้ ผลลัพธ์ต้องแม่นยำและมีหลักฐาน AI ไม่เพิ่มคุณค่า และเพิ่มความเสี่ยงสร้างตัวเลขที่ไม่มีหลักฐาน (รายละเอียดใน [`AI_USE.md`](AI_USE.md))

## 8. ข้อจำกัดและสิ่งที่ยังไม่ควรนำไปใช้จริง
- lead time เป็นข้อมูลสังเคราะห์ ผลความเสี่ยงบางส่วนจึงเป็นผลของค่าที่ทีมตั้ง
- ยอดขายต่อ SKU น้อย (ราว 18 บรรทัดออเดอร์ต่อ SKU ใน 3 เดือน) ค่าเฉลี่ยต่อวันแกว่งได้
- สต็อกมี snapshot เดียว ไม่มีประวัติ และใช้วันที่ snapshot (2026-07-31) เป็น "วันนี้"
- ไม่ทราบว่าสถานะ `processing` หักสต็อกแล้วหรือไม่
- ระบบเป็นเครื่องมือช่วยตัดสินใจ ไม่สั่งซื้อจริง มนุษย์อนุมัติเสมอ และไม่รองรับหลายคลัง
